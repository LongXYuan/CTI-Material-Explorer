# CTI Material Explorer — 数据字典

## 1. 文档目的

本目录用于存储 CTI Material Explorer 的结构化材料数据。

目标游戏版本为 CTI 0.46a。所有与游戏相关的事实都必须经过核实，才能被视为已确认的数据。

## 2. 文件说明

| 文件 | 用途 |
|---|---|
| `materials.json` | 保存材料记录、适用用途、部件、属性、特殊效果及材料整体验证状态 |
| `parts.json` | 统一管理部件 ID 和多语言名称 |
| `stats-definitions.json` | 定义材料属性及其数据类型、名称和单位规则 |
| `sources.json` | 保存数据来源记录 |

## 3. 多语言规范

多语言名称使用以下语言标识：

- `zh`：中文
- `es`：西班牙语
- `en`：英语

如果某种语言的名称尚未提供或核实，使用 `null`。

不得随意编造未经核实的翻译。

## 4. ID 命名规范

- 每种材料必须拥有唯一的 `id`。
- 每个部件定义必须拥有唯一的 `id`。
- 每个属性定义必须拥有唯一的 `id`。
- 每条来源记录必须拥有唯一的 `id`。
- 同一实体类型中不得存在重复 ID。
- ID 应保持稳定，不应依赖可修改的多语言显示名称。

ID 是项目内部使用的标识符，不一定等同于游戏内部 ID。

## 5. 用途与部件关联

`materials.json` 中的 `applicability` 用于关联材料的用途和适用部件。

目前支持以下用途 ID：

- `armor`：护甲
- `tool`：工具
- `ranged`：远程
- `special`：特殊
- `other`：其他

材料记录中的部件 ID 必须能在 `parts.json` 中找到对应定义。

同一种材料可以适用于多个用途和部件，不应因此重复创建材料主记录。

## 6. 材料属性与来源

材料属性保存在 `materials.json` 的 `stats` 字段中。

属性 ID 必须引用 `stats-definitions.json` 中已经定义的属性。

每项属性都应能够追溯到一个或多个来源 ID。被引用的来源 ID 必须存在于 `sources.json` 中。

来源记录应包含足够的信息，以便开发者重新定位和核实原始资料。

不能仅因为存在来源记录，就认定相关游戏数据已经核实。

## 7. 数据验证状态

每种材料通过 `verification.status` 记录整体验证状态。

`unverified` 表示该材料的相关游戏信息尚未完成核实。

材料整体验证状态与单项属性的来源追溯是两个不同的要求：

- 整体验证状态说明材料记录的核实进度。
- 单项属性的来源信息说明该属性依据什么资料录入。

JSON 语法验证通过，不代表材料数据真实或准确。

## 8. 数据质量规则

- 所有 JSON 文件必须符合标准 JSON 语法。
- JSON 文件中不得直接添加注释。
- 同一实体类型中不得存在重复 ID。
- 不得引用未定义的部件、属性或来源 ID。
- 未知数值不得直接使用 `0` 代替。
- 已验证的属性必须保留可追溯的来源信息。
- 游戏相关信息必须针对目标版本 CTI 0.46a 进行核实。
- 测试数据必须明确标记，不得冒充真实游戏数据。

## 9. 维护原则

修改数据结构时，应同步更新本文件。

新增材料时，应先检查材料 ID 是否重复，并确认用途、部件、属性和来源之间的关联正确。

在建立自动化校验程序后，应在提交材料数据前运行校验，确保数据结构与关联关系符合项目规范。
